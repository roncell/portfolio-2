    Inside the embeddings

    The first model grouped songs by language, not theme

    The April prototype embedded lyrics with off-the-shelf XLM-R. Projecting those 84 vectors to two dimensions shows the problem a cross-language recommender has to overcome.

    Select a point to load it as the seed in the demo above.
    0.984–1.000
    raw cosine range across all 3,486 pairs
    37%
    of variance on the first axis, which splits romanized Korean from English

    Raw XLM-R mean-pooled vectors are nearly parallel: every pair of songs scores between 0.984 and 1.000. Rankings still exist, but the scores carry little signal. Subtracting the corpus mean (the Centered mode in the demo) spreads them out without changing the order much.

    The bigger problem is clustering. Romanized Korean lyrics form a tight group that sits apart from English regardless of theme, so a Korean seed mostly returns other romanized Korean songs. A cross-language recommender needs the opposite.

    The later design attacks this from two sides: LaBSE replaces XLM-R as the encoder, since it is trained to place translations close together, and the pipeline generates cross-language positive pairs from shared playlists, so contrastive fine-tuning pulls songs people listen to together into the same region whatever the language.

    Fine-tuning loss on the pipeline's pairs

    LaBSE with MultipleNegativesRankingLoss, batch 32, lr 2e-5, 50 epochs, then cast to FP16 and logged to MLflow.

    Loss drops from 3.84 to 0.004 in 651 s on one GPU. At about 330 pairs per epoch (25.3 samples/s × 651 s ÷ 50) this mostly shows the model memorizing a small set. More pairs per slice is the fix, which puts the pressure back on the pipeline.

    End-to-end API latency

    50 requests to /recommend-playlist per concurrency level, before Triton. Each request calls Spotify and lyrics.ovh, then embeds and ranks.

    Median latency grows roughly linearly with concurrency (1.45 s at 1, 13.5 s at 16) while throughput falls from 0.64 to 0.08 req/s, so requests were being processed one at a time.

    Architecture

    Where the pipeline sits in the full system

    Teal boxes are the data pipeline I owned. The rest is the team's training, serving, and deployment stack, provisioned on Chameleon Cloud with Terraform, Ansible, and ArgoCD.

    Chose: per-slice JSON outputs

    Resumable over fast

    Each slice writes its own uri_to_track, track_to_embedding, and positive_pairs file. Restarts are cheap and slices never overwrite each other. The cost is many small JSON files that training has to merge, and embeddings stored as JSON floats, which is bulky.

    Chose: MinIO plus a block volume

    S3 semantics without a cloud bill

    MinIO gave the team an S3-compatible bucket that MLflow could also use as its artifact store, running in Docker on the same lease. The trade-off is operating it yourself: the training scripts still pulled data over scp from the block volume.

    Chose: playlist co-occurrence as the label

    Weak labels, no annotation

    Two songs from the same playlist in different languages count as a positive pair. That needs no human labels and scales with MPD, but it is noisy, since playlists mix moods, and it yields few pairs when playlists are mostly one language.

    Chose: language ID on a lyric window

    Cheap, and fragile on romanized text

    Language is detected on characters 100–200 of the lyrics, which skips intros and keeps detection fast. Romanized Korean, common in MPD lyrics, is exactly the case where a short Latin-script window is easy to mislabel.

    Repo triage, October 2026

    What runs, and what would need work

    Works as committed

    • Pipeline notebook ran on Colab over 10 full slices; the output is saved in the notebook.
    • Fine-tuning script completed a 50-epoch run and logged the model to MLflow.
    • Benchmarks and optimization sweeps produced the reports above.
    • Infrastructure as code for a 3-node Kubernetes cluster, MinIO, MLflow, Postgres, and staged ArgoCD deploys.

    Missing or broken

    • No model or data in the repo. data/ and model/ are gitignored; the API expects them on disk.
    • API won't start as committed. src/api/app.py uses MlflowClient without importing it, and get_track_info returns None where a tuple is unpacked.
    • Query and index embeddings disagree. train/src/eval_model.py loads the fine-tuned model but encodes queries with base LaBSE.
    • Config drift. Compose passes SPOTIFY_CLIENT_ID but the code reads CLIENT_ID; Prometheus scrapes port 8000 while the app listens on 5000; src/utils/data.py has a syntax error.
